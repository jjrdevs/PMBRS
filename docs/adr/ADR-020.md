# ADR-020: BoOX Sync Transport — Device-Push (Headless App), LAN-First + Cloud Fallback

| Field     | Value                          |
|-----------|--------------------------------|
| Status    | Accepted                       |
| Date      | 2026-08-21                     |
| Context   | See below                      |
| Decision  | See below (D1–D6)              |
| Consequences | See below                    |

**Supersedes-in-part:** ADR-019, decision D2 ("custom BooxSync agent … deferred")
and D5 ("ADB file pull … the transport"). D1 (PC-side LLM-vision OCR), D3 (engine
slot), and D4 (journal-modality adapter) of ADR-019 are **unaffected and remain in
force**. See the "A vs B" note in ADR-019 §Consequences: this ADR **is** the re-scoped
option B, and per ADR-019's own escape hatch it reuses the identical OCR engine,
manifest-diff idempotency, and ingest contract — only the transport plane changes.

**Evidence record:** the facts cited here were verified on a live NoteAir3 (serial
`4EF2D7E9`, USB `usb:1-3`, Android 12, `user/release-keys`) and on the dev host on
2026-08-21:

- Device: `sys.onyx.idledelay=2500` (screen asleep after ~2.5 s);
  `settings get global wifi_sleep_policy`=**2** (Wi-Fi drops on screen sleep);
  Wi-Fi logs show self-initiated reconnects at 02:32 / 07:32 / 08:14
  (~hourly, ONYX sync behavior); `com.google.android.gms` installed;
  `battery_saver`=0, `ignore_background_data`=null (no ONYX app-freeze policy
  observed); Wi-Fi-only (no SIM/RIL); `curl` present; `init.svc.adbd`=running.
- Host: `~/.cloudflared/config.yml` live with `mobile-sync.jjrdev.com` →
  `127.0.0.1:8788`; `scripts/pmbrs_host_sync_ingest.py` has **no** auth
  (verified by grep, 2026-08-21) and a single route
  `POST /api/v1/artifacts/sync`.
- Reusable client code: `pmbrs/mobile/` (Kotlin: `sync/` queue + WorkManager,
  `network/` endpoint-selection + bearer-token client; `SyncApi.kt` pins the
  route/payload shape).
- Stage-1/2 state on disk: `src/pmbrs/ingestion/boox/` (producer/adb/manifest/ocr),
  `scripts/pmbrs_boox_nightly.py`, `~/.pmbrs-private/state/boox_sync_manifest.json`,
  17 synced note pages under `~/.pmbrs-private/store/raw/journal/`.

## Context

ADR-019 shipped a working BoOX→journal pipeline whose transport is **PC-pull over
ADB** in a scheduled pass (Stage 2: `pmbrs_boox_nightly.py`). It works, and Stage-2's
"device unreachable → graceful no-op (`exit 3`)" is correct behavior, but the
*transfer window* is now the constraint:

1. **The sync only succeeds if the Boox is awake, powered, and reachable at the
   scheduled moment.** The device's `wifi_sleep_policy=2` means it is LAN-invisible
   for essentially all of its idle time (e-ink device, `idledelay=2500`), and nothing
   can reach a *powered-off* device at all.
2. **USB-tethered ADB is the primary path today** and ADB-over-LAN is the non-USB
   fallback (ADR-019 D5) — both assume the device is in a reachable state we do not
   control.
3. **The ingest server has no authentication.** Acceptable on a USB/LAN trust
   boundary (ADR-019 D5 rationale); *not* acceptable the moment the device can reach
   the ingest endpoint over the public tunnel — and the payload class is now raw
   handwritten journal pages (the recon sample transcript is deeply personal), i.e.
   more sensitive than phone telemetry.
4. User decisions (2026-08-21): move to **LAN-first + cloud fallback** network
   transport (mirroring `pmbrs/mobile`), with **separate hostname + token**
   for the Boox; **no visible UI** on the device (confirmation/notification is the
   debug surface); the ADB sweep is **retained specifically as the net for a
   powered-off device**. These decisions select ADR-019's deferred option B.

The question this ADR answers: **what is the transport plane, what runs on the
device, and what must change on the PC before the device can safely use it?**

## Decision

### D1 — Transport plane: device *push* over HTTP, LAN-first + tunnel fallback

The transport is **device-originated HTTPS push** of the sync payload
(ADR-019 D1–D4 unchanged: the device ships **input** — page PNG + note UUID + page
order + sha256 — and the PC still runs OCR and writes the journal artifact).
Endpoint selection is **LAN first, tunnel fallback**, the same dual-endpoint pattern
as `pmbrs/mobile` (local URL when on the home network, `https://boox-sync.jjrdev.com`
otherwise).

Rationale:
- Converts the transfer window from "PC must reach the device at T" to "device moves
  as soon as it naturally has a network window" — the device's own ~hourly Wi-Fi
  windows (02:32/07:32/08:14 evidence) become sync opportunities with **zero**
  scheduled-wake cost.
- Removes USB/ADB from the production path (ADB remains for dev, deep-debug, and the
  D6 sweep).
- Matches the already-proven, already-written client architecture in
  `pmbrs/mobile` — this is replication of a pattern, not invention of one (§15 low
  entropy).
- **ADR-019's escape hatch is respected verbatim**: identical OCR engine, identical
  ingest contract, identical manifest idempotency; only the Kotlin transport and the
  producer's *source-of-files* differ.

### D2 — Auth boundary: dedicated hostname + dedicated bearer token (pre-device prerequisite)

The Boox gets its **own** tunnel hostname, **`boox-sync.jjrdev.com`** (cloudflared
ingress entry → same `127.0.0.1:8788` service), and its **own** bearer token. It
does **not** share `mobile-sync.jjrdev.com` or any future phone token.

- `pmbrs_host_sync_ingest.py` gains bearer-token auth on the sync route. This is a
  **hard prerequisite before the device app is pointed at the tunnel** — the current
  server trusts every caller, which is acceptable ADR-019-D5 LAN/USB-only and is not
  acceptable with a public hostname in the critical path.
- Tokens live outside the repo (`~/.pmbrs-private/config/`), with a rotate/issue
  operation; revocation of the Boox token must not affect the phone and vice versa.
- Rationale: different **data class** (raw handwriting pages vs phone telemetry),
  different **blast radius** (revoke without touching the other device), independent
  observability per device (per-hostname logs/rate limits). Mirrors the mobile
  fallback plan's own rule that the tunnel exposes only the ingestion API, never the
  raw store.

### D3 — Device footprint: headless foreground-service app; the notification is the UI

The Boox runs a **headless Android app**: no screens, no Compose, no settings UI.
The required foreground service (Android 12 background restrictions + Doze survival)
carries a **low-importance persistent notification** — e.g.
`BooxSync · 3 queued · last sync 02:14 ✓ (3/3 acked)` — which simultaneously
*is* the user-confirmed debug surface (2026-08-21 decision), alongside `logcat`
and the hub's ack trail.

- The app exists primarily to (a) let the foreground service run, (b) host the
  durable upload queue (something must survive reboot/Doze and remember what has
  and hasn't been ACKed), and (c) carry the exact-alarm + connectivity-callback
  logic. Without a persistent process, nothing remembers an un-ACKed upload after a
  reboot — and the NoteAir reboots on battery cycles.
- Reuse from `pmbrs/mobile`: `sync/` (queue DB, WorkManager + foreground,
  retry/backoff) and `network/` (endpoint selection, token client). Collectors and
  UI are **not** ported.
- New Boox-specific code: note-cache watcher (`.ksync/document/<uuid>/` +
  `.noteCache/thumbnail/` page tree, sha256-diffed), uploader, one daily
  `setExact` alarm, `ConnectivityManager` Wi-Fi-available callback.
- Required one-time grants: `MANAGE_EXTERNAL_STORAGE` (Android 12 gate on reading
  other apps' shared storage), `FOREGROUND_SERVICE`, `SCHEDULE_EXACT_ALARM`,
  `INTERNET`, `POST_NOTIFICATIONS`, plus "Don't optimize battery" for the app.
- Rationale: the user asked for *no* app/visuals; the minimum Android 12 footprint
  that satisfies that is exactly this. The Termux/watch-loop alternative was
  considered and rejected: it gets Doze-killed within minutes, has no durable
  queue, and is exactly the failure mode the `pmbrs/mobile` queue design exists to
  prevent.

### D4 — Wake strategy: opportunistic + one exact daily alarm; no push-dependency

| Path | Mechanism | Cost |
|------|-----------|------|
| Opportunistic | `ConnectivityManager` Wi-Fi-available callback + note-watcher → upload **iff** queue non-empty | ~0 (event-driven; reuses the device's own Wi-Fi windows and any user pickup) |
| Daily fallback | one `AlarmManager.setExact` (default 02:00, configurable) → wake → Wi-Fi → upload-if-queued → release wake lock | one 30–60 s Wi-Fi burst/day, only when queued (<1%/day) |
| Powered-off | **unreachable by design** → covered by D6 (PC-side sweep) | existing sweep cost |

- **FCM is explicitly not in the critical path.** GMS is present on this build, but
  on a Wi-Fi-only, screen-sleeping device pushes only land within GMS's own
  reconnect windows — it is a future *nudge-at-best*, never a wake. The app's
  network layer stays FCM-shaped (separate endpoint/token/queue) so adding it later
  is a module, not a rewrite.
- We do **not** force `wifi_sleep_policy=0` (keep radio up through sleep) — the
  more expensive option, against the user's battery preference.
- Rationale: the device's verified self-wake behavior (hourly Wi-Fi reconnects)
  means "event-driven sync" already fires multiple times per day at near-zero
  cost; the exact alarm exists only to guarantee at-least-one window per day
  without keeping the radio or CPU hot.
- **Cadence note (Constitution §14-6):** this does *not* add a second PMBRS
  cadence authority. The nightly *pipeline* cadence (ingest→align→feature) is
  unchanged; what changes is only **when the transport delivers files**, and the
  existing single nightly passover batch already consumes "whatever arrived since
  last run" (manifest-diffed, idempotent). The device-side alarm is transport
  scheduling on a separate device, not a PMBRS batch cycle. No second scheduler
  APK (per ADR-019 positive consequences) — the uploader app is the *only*
  Boox-side software.

### D5 — Idempotency: two manifests, one sha256, both already-exist

- **Device side — "uploaded?"**: the queue DB (pending → uploading → acked),
  marked acked only on hub-ACKed `syncedIds` — the mobile app's two-layer state,
  already proven in `pmbrs/mobile`.
- **PC side — "OCRed?"**: the existing Stage-2
  `~/.pmbrs-private/state/boox_sync_manifest.json` (per-note/per-page sha256),
  unchanged in meaning.
- A page that is pushed but not yet OCRed therefore neither re-uploads
  (device manifest) nor double-OCRs (PC manifest). No new dedupe logic; the
  producer's source-of-files becomes `union(inbox, adb_tree)` so both delivery
  paths feed the same pipeline without cutover risk.

### D6 — ADB is retained as dev/debug transport and as the powered-off net

- The Stage-2 `scripts/pmbrs_boox_nightly.py` sweep is **kept** (not retired):
  it is the only mechanism that works when the device is powered off, and at
  steady state it costs ~0 (empty inbox → `exit 3`/no-op in seconds).
- ADB remains the development transport and the deep-debug surface (and the
  token-rotation channel — a new token is loaded onto the device over ADB once).
- Cutover criterion (Stage-3 §8): run both in parallel one full week; the sweep
  must report 0 new finds after day 2 while every new note arrives via push; then
  ADB-debug can be left on or off at the user's discretion with no functional loss.
- Rationale: keeps a **fully reversible** path (turn the app off, the Stage-2
  system still works), which is the cheapest possible insurance during the week
  the device app is young.

## Consequences

### Positive

- **Notes sync on the device's own schedule, from anywhere** — the standing
  weakness of Stage 2 (transfer-window coupling) is removed from the production
  path; USB-tether and ADB-debug are no longer requirements.
- **Battery-lean by construction**: event-driven primary path + one bounded daily
  alarm, no persistent radio/CPU, no FCM keepalive, no polling loops.
- **Zero new pipeline surface**: OCR engine slot, artifact contract, store bucket,
  provenance shape, and the single nightly cadence authority are untouched
  (ADR-019 D1/D3/D4 in force). This ADR changes *delivery*, not *processing*.
- **Security is a feature of the design, not a bolt-on**: the public-tunnel path
  requires bearer auth *before* it exists on any device; per-device token and
  hostname give independent revoke/audit for the most sensitive data class we
  carry (raw handwriting pages).
- **Fully reversible**: sweep + ADB remain live through and after cutover; the
  device app can be disabled with zero feature loss (Stage-2 behavior is the
  fallback).
- **Debug surface without UI**: persistent notification + `logcat` + hub ACK log
  cover the user's "confirmation of some kind" requirement with no visible app.

### Negative

- **New Android codebase** (the deferred scope-B cost ADR-019 priced): a headless
  app, a small new set of permissions to grant on the device (incl.
  `MANAGE_EXTERNAL_STORAGE`), and an APK install/update channel (kept simple:
  APK in the repo, sideload over ADB).
- **One more always-present app on the device** — foreground service + persistent
  notification, subject to ONYX/Android policy changes across OS updates; if ONYX
  ships an app-freeze mode, D3's service needs that exemption added.
- **The ingest server gains an always-on authenticated attack surface** (a public
  hostname) — mitigated by the token, but it adds rotation hygiene to the ops
  list (a leaked token means raw journal pages are exfiltrable until revoked).
- **Two delivery paths during cutover** means for one week the same note could
  arrive both pushed and swept; D5's shared sha256 dedupe makes that harmless,
  but it is still a state to reason about until cutover completes.
- **Titles remain unrecoverable** — unchanged from ADR-019 (private DB, recon Gaps
  §2); the transport change does not alter this.

### Neutral / Trade-offs

- **ADR-019 is amended, not superseded.** Its D1 (PC-side LLM-vision OCR), D3
  (engine slot), D4 (journal adapter) are untouched; D2's "deferred" agent
  is adopted with the narrower footprint of D3; D5's ADB transport is replaced
  as the *production* path and retained per D6. When ADR-019's status line is
  next touched, it should read *"Accepted (D2/D5 transport decisions
  superseded in part by ADR-020)"*.
- **Boox engagement telemetry** (note open/close, stroke activity) remains out of
  scope (ADR-019 §Consequences) — but D3's app shell is deliberately
  app-host/collector-agnostic, so a future telemetry ADR adds collectors, not a
  second app.
- **FCM-as-nudge, `wifi_sleep_policy=0`, and Termux** are all viable fallbacks if
  the D4 strategy proves insufficient in the wild; none are required, and adding
  any is a bounded local change per the design above.
- **Books→Boox delivery** stays out of scope (ADR-019 user decision 3, unchanged);
  the uploader app is a push-only agent and gets no download path.
