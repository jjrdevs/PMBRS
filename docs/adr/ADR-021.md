# ADR-021: Galaxy Watch 7 biometrics ingest into the canonical 60-s grid

Status: accepted (2026-08-31)
Supersedes: n/a (adjacent to ADR-020 boox file route; reuses that transport)

## Context

Boox ADR-020 already established the device→host batch-push pattern
(export file + sha256 over the Cloudflare tunnel to the local ingest server,
0600 inbox, nightly parser→canonical raw store). We need the same shape for
biometrics: the user's Galaxy Watch 7 produces 60-s HR bins, watch-derived
5-min HRV (SDNN/RMSSD), plus stress/sleep.

Health Connect is 100% empty on Samsung (0 records, permanent) and there is
no raw IBI access, so the only dense source is Samsung Health's native
**CSV/JSON file export** — pulled as a batch (overnight) rather than a live
stream. The export lives in the user's Samsung Health app on the Samsung
phone.

Constraints fixed by prior work:
- No paid SDK; no live per-beat stream.
- "True" HRV only exists as watch-computed SDNN/RMSSD windows (~17/90 days,
  sparser recently). HR (42,655 bins, 2021→2026) is the dense primary signal.
- Between the two we can derive a *proxy* HRV (RMSSD of rolling 60-s HR) —
  tier-2, labelled as inferred, never passed off as true HRV.

## Decision

**D1 — Watch export is the biometrics source.** Samsung Health's per-modality
CSVs (heart_rate, hrv, stress, sleep_stage, sleep) + the JSON HR-bin arrays
are the canonical ingest, batched overnight. Health Connect remains excluded.

**D2 — Transport reuses the ADR-020 pattern, sibling of boox.** A new host
route `POST /api/v1/wearable/files` on the existing `pmbrs_host_sync_ingest`
server (port 8788 via the shared `mobile-sync` tunnel). Auth = bearer token
with the existing `mobile` role in the same token store (no new role needed;
the route is route-dispatched, same as the boox route's `boox` role); path
allowlist restricted to the watch-export subdirs; sha256 verified on the host
before accept; files land in a 0600 inbox under `store/inbox/wearable/`.
Boox/mobile routes are untouched.

**D3 — No live heartbeat stream.** Sync is push-on-completion (nightly batch),
matching "batched overnight" — not a continuous per-beat feed.

**D4 — Producer emits the canonical 9-key artifact per 60-s window.**
Reusing `pmbrs.ingestion.boox.artifact`'s base shape (ADR-017 D2) so the
canonical window contract and the raw-store writer stay uniform. The payload
carries the window's modalities with explicit coverage/missingness, so a 60-s
window with only HR has `hrv: null` + `hrv_present: false` rather than 0.

**D5 — Modalities, tiers, and honesty:**
- Tier 1 (dense): `heart_rate` — 60-s bin mean/min/max bpm.
- Tier 2 (inferred): `hrv_proxy` — RMSSD over rolling 60-s HR; **labelled
  `method: "rolling_rmssd_60s"` and `derived_by_watch: false`** so analysis
  never confuses it with true HRV.
- Tier 3 (episodic): `hrv` — watch SDNN/RMSSD windows, only where present.
- Tier 4: `stress`, `sleep_stage` (stage codes), `sleep` (summary).

**D6 — Idempotency:** file-level sha256 manifest (like boox's) drives
`needs_processing`; the canonical writer is keyed
`<artifactId>-<createdAtMs>.json` and is deterministic, so re-runs are no-ops.

## Consequences

- New: `POST /api/v1/wearable/files` route (authz via existing `mobile` role) +
  `wearable` inbox dir; `src/pmbrs/ingestion/wearable/` (parsers, producer,
  proxy, grid alignment); a wearable nightly script + cron; phone-side export
  trigger.
- Canonical window now carries a `heart_rate` modality; downstream behavioural
  model gains a dense physiological prior. `hrv_proxy` is available but must be
  treated as a lower-fidelity feature.
- Storage growth: one JSON file per 60-s window across ~5 yrs of HR ≈ large
  but dedup'd and sha-stable (re-runs write 0 new files).
- Not chosen: Health Connect (no data), raw IBI (unavailable), paid HRV SDK
  (excluded by constraint).
## Amendment A — Transport model: inbox-first, ADB fallback (2026-09-03)

**Problem.** The nightly script shipped with `--source phone` as the default,
i.e. ADB-pull-only. The first scheduled runs (2026-09-01 → 09-03) all
failed exit 3 with `device not reachable over ADB: 'R5CW61SY12N'` because the
phone is not guaranteed to be on ADB at 03:00 local. The boox nightly
(ADR-020 D5) solved the same shape by defaulting to the inbox route — the
Boox pusher drops files in `store/inbox/boox/` before sleep and the nightly
just drains. Wearable never made the equivalent flip, so it stayed pull-only.

**Decision (2026-09-03).** `pmbrs_wearable_nightly.py` now supports a
first-class `--transport auto|inbox|adb` flag, defaulting to `auto`. Priority
order:

1. `--source-dir DIR` (explicit local layout; legacy `--source local-dir`).
2. **Inbox** (`auto`/`inbox`): run the producer directly against
   `store/inbox/wearable/` (default `~/.pmbrs-private/store/inbox/wearable/`,
   overridable via `--inbox-root` or `PM_BRS_WEARABLE_INBOX`). The file
   layout is byte-identical to an ADB-pulled phone export, so the existing
   parser and manifest are untouched.
3. **ADB fallback** (`auto` only, inbox empty): pull the newest Samsung
   Health export over ADB as before.

Behavioural contract:

- `--transport inbox` (no ADB): if the inbox is empty, the script exits 2
  with a one-line WARN — a *benign no-op*, not an error. This is the state
  the 03:00 nightly is now expected to land in when the phone-side pusher
  has not yet delivered an export.
- `--transport auto`: if the inbox is empty, fall back to ADB; if ADB is
  also unreachable, exit 3 with the same message as before. `auto` is the
  recommended default because it keeps both doors open.
- `--source phone` / `--source local-dir` remain as deprecated aliases for
  `--transport adb` and `--source-dir` respectively (backward-compat). New
  prompts should use `--transport auto`.
- Exit code 2 ("nothing to do") is re-used for the benign empty-inbox case;
  the boox nightly already treats 2 as benign, so the cron prompt treats it
  as non-failing.

**Consequences.**

- The phone-side pusher is now the *primary* data path for the wearable
  nightly, not the fallback. The nightly becomes a thin "drain the inbox"
  job, matching the boox nightly.
- The host route `POST /api/v1/wearable/files` (already built and live per
  ADR-021 D2) is the single delivery channel the pusher uses. ADB remains
  the legacy recovery path.
- The nightly cron prompt (job `282d7c0858d5`) runs `--transport auto --json`
  and reports exit 2 as a benign "nothing to sync" — no longer treated as a
  failure the operator has to investigate.

**Files changed.**

- `scripts/pmbrs_wearable_nightly.py` — transport model (this commit).
- `~/.hermes/cron/jobs.json` — wearable job prompt, `deliver=local`,
  transport-aware reporting.
- `docs/adr/ADR-021.md` — this amendment.
