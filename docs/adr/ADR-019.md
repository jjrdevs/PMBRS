## Context

We want to bring **handwritten note text** from a BOOX NoteAir3 into the PMBRS journal
pipeline. The constitutional fit is already there: `journal` is a first-class modality in
the ingestion catalog (`docs/ingestion/overview.md`), it is the *subjective/declarative*
authority lane (`docs/contracts/modality_contract.md`), and the raw store already reserves
a `journal/` bucket in the running ingest
(`scripts/pmbrs_host_sync_ingest.py` → `~/.pmbrs-private/store/raw/journal/`). What's
missing is an **adapter** that turns the tablet's notes into journal artifacts.

Stage-0 recon established the hard constraints this ADR has to work within:

- **Notes are stroke ink + scene-graph JSON, never text** (recon §"Key facts", fact 1).
  There is nothing to copy directly; **text must be generated**.
- **No note index is exposed in shared storage** — titles/hierarchy sit in the app's
  private Couchbase-Lite DB, not root-accessible (recon fact 2, Gaps §2).
- **The OCR engine is proven local**: `qwen3.8:27b` on local Ollama transcribed the user's
  messy cursive at ≈95% clarity on 500 px renders; `qwen3.6-27b` has **no vision
  capability** and is not a candidate (recon fact 4, A/B evidence).
- **ADB is the working transport** from the dev host; MTP is not mountable here; ADB shell
  on the e-ink device is slow (recon §Device & access).
- **The existing device→hub pattern** (Kotlin client → `POST /api/v1/artifacts/sync`) and
  the **external scheduling/notification APK**
  (`personal-task-system/task-notify-android`) are the established planes.

User decisions that bound this ADR: (1) **the PC does the OCR**, not the Boox; (2) the
Boox stays on ADB/debug during development; (3) **scope is notes only, no books→Boox**;
(4) prefer **LLM-vision** OCR, keep it **local**, and leave room to later train a model on
the user's own handwriting.

## Decision

### D1 — OCR engine: LLM-vision over rendered page images (PC-side)

Text is produced by a **vision-language model run on the PC**, operating on the **rendered
page PNGs** (`.noteCache/thumbnail/page/<pageid>/*.png`, `.noteCache/thumbnail/<note>/.png`).
We do **not** re-implement the Skia ink renderer and do **not** ship a classic OCR engine
(Tesseract/Paddle). The ink `shape/*.zip` bundles and the scene-graph `*.pb` models are used
at most for **page geometry / page ordering / blank-page detection**, never as the OCR
source.

Rationale:
- §16 (local-first) + §5 (batch-first): this is a local PC batch job, no device compute,
  no cloud.
- The LLM-vision path is **proven** on the user's handwriting (recon A/B); a classic OCR
  engine would have failed on it and is not installed.
- Re-implementing the Skia renderer to get full-res ink is a discrete sub-project that buys
  very little over the 500 px renders that already worked (recon fact 3) — we only reach for
  it if a real multi-page sample proves thumbnails insufficient (recon Gaps §3).

### D2 — The PC is the coordinator; the Boox is a transport + data source

The PC orchestrates the whole pipeline: enumerate notes, resolve pages, pull page images,
run OCR, emit artifacts, ingest. The Boox contributes only (a) its note-store tree and
(b) the ADB pipe. **No custom BOOX app** is built for v1 (the "BooxSync agent /
authenticated-HTTP custom protocol" idea from the original notes is **deferred** — it is
scope B, validated against ADB availability and only revisited if the ADB path proves
insufficient). This keeps v1 free of new Kotlin and of an unvalidated transport.

Rationale: minimal new surface; reuses the proven `adb pull` transport; matches the
"PC-coordinated, manifest-diffed, idempotent batch" shape in the original notes without
the agent complexity.

### D3 — Default OCR engine: local Ollama `qwen3.8:27b`, behind an engine slot

The OCR call targets **local Ollama** (`http://127.0.0.1:11434`) with model
**`qwen3.8:27b`** (or the `my-qwen38-*` high-context variants), low temperature, vision on.
The concrete engine is abstracted behind an **OCR engine slot** so a future model —
notably a model **fine-tuned on the user's own handwriting** — is a config change, not a
code change. The engine name is recorded in provenance
(`ocr_engine: "qwen3.8:27b-ollama-local"`, `model` = exact name) so every artifact is
auditable for which engine produced it (§Interpretability).

Rationale: local + private + free (§16); proven to work; slot design honors the user's
explicit "we may need to train on my handwriting later" without coupling the pipeline to
any model.

### D4 — BoOX is a new `journal`-modality ingestion adapter (not a new modality)

BoOX produces **subjective/declarative `journal` artifacts** via the existing ingest
contract — the same record shape the running ingest already writes
(`artifactId, source:"journal", payload, createdAtEpochMs, schemaVersion, deviceAlias,
provenanceMetadataJson, ingestedAtEpochMs, ingestStatus`). No new modality type, no new
store bucket, no new API route. The adapter is a new **producer** (Python) under PMBRS that
talks to the existing `POST /api/v1/artifacts/sync` endpoint
(`scripts/pmbrs_host_sync_ingest.py`, default port 8765, or the
`https://mobile-sync.jjrdev.com` domain per ADR-017 D4).

Rationale: `journal` already exists and is the correct authority lane for freeform
handwritten notes; reusing it maximizes reuse and keeps downstream alignment/feature
stages (which key on modality) untouched.

### D5 — Transport: ADB now, LAN (`adb tcpip`) supported, manifest-diffed and idempotent

Transport is **ADB file pull** (`adb pull` of the note tree / page PNGs). For non-USB use,
the Boox is switched to ADB-over-LAN with `adb tcpip 5555`. Every run diffs a **manifest**
(`~/.pmbrs-private/state/boox_sync_manifest.json`: per-note `uuid`, dir `mtime`, per-page
PNG `sha256` + `dims`) so re-runs are idempotent — unchanged pages are not re-OCR'd. No new
credential, no new device auth token: ADB over the trusted link is the auth boundary
(boox-side §16 local trust; mirrors the "trusted-network" posture of
`mobile-collection.md`).

Rationale: ADB is the only transport the recon proved works from the dev host;
manifest-diff + idempotency make repeated nightly passes cheap and safe; LAN support removes
the USB-tether requirement without adding a second protocol.

## Consequences

### Positive

- **Ships a real feature with zero new device code**: a `journal` adapter that turns
  existing BoOX notes into PMBRS journal artifacts and lands them in the already-wired
  `raw/journal/` store. Immediately consumable by the existing alignment → feature →
  embedding pipeline.
- **Local + private + free** (§16). No cloud OCR, no new vendor, no new token.
- **Proven OCR quality** on the user's actual handwriting (recon A/B), and a **clean model
  slot** for a future handwriting-specific model.
- **Zero new infrastructure**: reuses existing ingest endpoint, store bucket, provenance
  record shape, and the external scheduling/notification APK for any user-facing "notes
  synced" reminder. We do **not** add a second scheduler (Constitution §14-6 / the existing
  batch cadence stays the single cadence authority).
- **Idempotent** and **auditable**: manifest-diffed re-runs; every artifact records
  `ocr_engine`/`model`/`source_page_sha256`.

### Negative

- **No note titles in v1** (private DB is not root-accessible, recon Gaps §2). Titles are
  recovered best-effort from the OCR text (heading/first line) or left blank. Users who
  relied on the Boox's own titles won't see them preserved.
- **Resolution tradeoff**: OCR runs on ~500 px thumbnails, which worked for the samples but
  is not guaranteed for very small / dense handwriting. Mitigation: v1 ships with the
  thumbnail path *and* a full-res renderer escape hatch to enable if a real multi-page note
  fails (recon Gaps §3).
- **ADB shell is slow** on the e-ink device (recon §Device). Large note volumes could make a
  single sync pass slow. Mitigation: idempotent manifest-diff keeps steady-state passes small;
  runs are batched and resumable; LAN transport removes USB latency.
- **One engine at a time.** We commit to qwen3.8:27b for v1. A future better-local model or
  a cloud LLM is possible via the slot, but that is a change, not a capability we ship now.
- **Boox-side OCR is out**; we never use the device's `aiassistant`. This is deliberate
  scope, not an oversight (decision D3 + user decision 1).

### Neutral / Trade-offs

- **A vs B (agent) remains open.** D2 defers the "custom BooxSync agent + authenticated HTTP
  protocol" build. If ADB proves insufficient (device unreachable, slow, or the user wants
  background auto-sync without USB), B is re-scoped using the *identical* OCR engine +
  ingest contract we ship here — B only adds a thin Kotlin transport, not a new pipeline.
  This is why D1–D4 stay stable across the A/B choice.
- **Boox engagement telemetry** (note open/close, stroke activity) is **out of scope** for
  this ADR. It would be a *separate* observational modality (like the mobile app's
  screen/telemetry collectors), not part of journal ingestion. ADRs a later one.
- **Books→Boox delivery** is explicitly **out of scope** (user decision 3). The device has
  `kreader`/`easytransfer`; a future "push books to the Boox" feature is a file-endpoint
  concern, not a PMBRS data concern, and is deferred.
- **Multi-page fan-out** handling is a Stage-1 implementation detail (recon Gaps §1): the
  adapter resolves note→page from `virtual/page/pb` (decode) with an mtime-ordered
  fallback. This does not change the ADR's decisions — only how the adapter enumerates
  pages under a note.
