# ADR-017: Storage Reality Alignment, Cadence Split, and Dashboard Hosting

| Field     | Value                          |
|-----------|--------------------------------|
| Status    | Accepted                       |
| Date      | 2026-08-19                     |
| Context   | See below                      |
| Decision  | See below (D1–D4)              |
| Consequences | See below                    |

## Context

The documentation and the running system have diverged across four decision
areas, and the PMBRS dashboard + ML-training work cannot be built cleanly on
top of ambiguity. Evidence gathered on 2026-08-19:

**Data store reality** — the single user-data root in every runtime artifact is
`/home/jjrdev/.pmbrs-private` (a.k.a. `~/.pmbrs-private`). It is declared in
`config/external_data_policy.json`, hard-coded in three scripts
(`pmbrs_hermes_readonly_setup.sh`, `pmbrs_publish_summary_to_hermes.sh`,
`pmbrs_host_sync_ingest.py`), and is the root that `chmod 700` is applied to.

Observed on disk (2026-08-19):

```
~/.pmbrs-private/
├── hermes-readonly/pmbrs_summary.json          # read-only snapshot for Hermes
├── state/pmbrs_runtime.json                     # runtime metadata
├── state/hermes_snapshot.json                   # published snapshot payload
├── state/scheduler_state.json                   # nightly scheduler checkpoint
└── store/
    ├── raw/{browser,desktop,journal,mobile,other}/sample.json   # 5 placeholder artifacts
    └── summary/pmbrs_summary_<epoch_ms>.json                   # timestamped snapshots
```

Declared in config but **not yet created on disk**: `store/pending` (ingest
queue) and `checkpoints/` (module checkpoints).

**The path the docs claimed is absent.** `~/.local/share/pmbrs` does not exist
on this host. Two docs still pointed there:
`docs/storage/architecture.md` (×2) and `docs/visualization/architecture.md`
(×1). `docs/PROJECT_SUMMARY.md` and `docs/index.md` are consistent with the
real path.

**The artifact record shape written by the running ingest**
(`scripts/pmbrs_host_sync_ingest.py`:
`artifactId, source, payload, createdAtEpochMs, schemaVersion, deviceAlias,
provenanceMetadataJson, ingestedAtEpochMs, ingestStatus`) is already fixed in
code. `docs/representation/training-pipeline.md` currently states "runs nightly
or weekly … full retrain … OR weekly" — conflating the passover cadence with
the training cadence. Neither "monthly" nor "nightly-passover" is expressed at
all.

**The domain** — `https://mobile-sync.jjrdev.com/` is the Android sync host
(fallback URL in `mobile/app/src/main/java/com/pmbrs/mobile/settings/SyncSettings.kt`;
`/api/v1/artifacts/sync` in `SyncApi.kt`). No dashboard route is defined yet.

**StorageAdapter** — the `StorageAdapter` protocol (save/get/query/
derive_from/mark_module_complete/get_last_run) is defined on paper in
`docs/module-contracts.md` but **not yet implemented anywhere**. This is the
actual blocker for the dashboard and the ML stubs.

## Decision

### D1 (C1) — Authoritative user-data root: `~/.pmbrs-private`

The user-data root of record is `/home/jjrdev/.pmbrs-private` (a.k.a.
`~/.pmbrs-private`). The XDG-style path `~/.local/share/pmbrs` that appears in
`docs/storage/architecture.md` and `docs/visualization/architecture.md` is
retired as canonical. Rationale:

- §16 (local-first, single-user) is better served by a **dedicated** private
  root with `chmod 700`, not a shared XDG directory where another tool's data
  could co-locate.
- All three scripts, the runtime, and the config already use it.
- The rename cost would be strictly higher than the cost of aligning two
  doc lines.

`docs/storage/architecture.md` and `docs/visualization/architecture.md` were
corrected on 2026-08-19 to match. The two "declared-but-not-yet-created"
subroots (`store/pending`, `checkpoints/`) are retained as part of the
authoritative tree per `config/external_data_policy.json`.

### D2 (C2) — Storage format: **plain JSON raw today; JSONL + SQLite index layer for derived/aligned artifact types in the future**

The running ingest
(`scripts/pmbrs_host_sync_ingest.py`) writes **one JSON object per file** to
`store/raw/<source>/<artifactId>-<createdAtEpochMs>.json`. That is the source
of truth for **raw** artifacts going forward. The JSONL + `events.db` target
described in `docs/storage/architecture.md` (ADR-001) is retained as the
**target for derived / aligned / feature / embedding artifact types** once the
`StorageAdapter` protocol from `docs/module-contracts.md` is implemented.

The concrete split:

| Layer | Format | Status | ADR ref |
|-------|--------|--------|---------|
| `raw/<source>/` | **One JSON per file** (the running shape) | **in use** | this ADR, D2 |
| `pending/` (ingest queue) | One JSON per file | declared, not yet exercised | this ADR, D2 |
| `checkpoints/` (module checkpoints) | One JSON per file | declared, not yet exercised | this ADR, D2 |
| `state/` (scheduler, runtime, snapshot) | One JSON per file | **in use** | this ADR, D2 |
| `hermes-readonly/` (summary snapshots) | One JSON per file | **in use** | this ADR, D2 |
| `alignment_mappings.jsonl`, `features/`, `embeddings/` | **JSONL per file per modality** | **target** once `StorageAdapter` exists | ADR-001 / ADR-010 |
| `events.db` (SQLite index) | SQLite | **target**, deferred until `StorageAdapter` ships | ADR-001 / ADR-010 |

Rationale:

- §11 (Artifact Architecture) — raw artifacts are immutable; the raw format
  should be the simplest, most stable, most diffable format we can offer.
  One-JSON-per-file is the simplest format and it is what the running
  pipeline already produces. Forcing the raw layer onto JSONL + SQLite before
  any derived pipeline exists would burn weeks on an implementation that
  nothing consumes yet.
- §5 (Batch-First) — the derived artifacts (aligned windows, feature vectors,
  embeddings) will be higher-volume, higher-velocity, and benefit from a
  columnar index. That is when JSONL + SQLite earns its cost.
- Module contract — `StorageAdapter` is the **single** abstraction both the
  dashboard and the ML stubs will sit on; the format question is
  implementation-detail to that adapter. Phasing raw (JSON) from derived
  (JSONL+SQLite) is the lowest-entropy way to honor the module contract
  without forcing the choice onto consumers.

**Concretely, this ADR unblocks the dashboard and ML stubs**: both will call
a future `StorageAdapter` that reads `raw/*.json` transparently and writes
derived artifacts in the format chosen for that layer (JSONL + SQLite
eventually). No consumer has to care about the split today.

### D3 (C6) — Cadence split: nightly passover, weekly training with monthly full-retrain floor

The docs had conflated "nightly" and "weekly" into a single training cadence.
This ADR separates the two concerns:

| Cadence | What runs | ADR ref |
|---------|-----------|---------|
| **Nightly** (scheduled batch) | Ingest → align → feature → summary snapshot → Hermes read-only publish (`pmbrs_publish_summary_to_hermes.sh`, `pmbrs_host_sync_ingest.py`, `pmbrs_runtime.run_cycle`) | this ADR, D3 |
| **Weekly** (default) | Incremental training run (warm-start from prior checkpoint) — `src/pmbrs/representation/train.py` when implemented | this ADR, D3 |
| **Monthly** (floor) | Full retrain (cold start, full re-fit) + proxy-evaluation suite + drift/quality gate before deployment | this ADR, D3 |
| **On feature drift** | Trigger a full retrain early (see `docs/representation/training-pipeline.md`, §warm-start) | this ADR, D3 |

Concretely:
1. Nightly: the existing batch cycles run, the summary snapshot is republished
   to `~/.pmbrs-private/hermes-readonly/`, and any new raw artifacts that
   arrived during the day are processed through the pipeline. This is the
   **passover** cadence.
2. Weekly: the ML training loop runs incrementally. If a checkpoint exists it
   is warm-started; otherwise it trains from the feature store. The output is
   a `behavioral_embedding` artifact plus a `clustering_result` (if the
   clustering stage is enabled).
3. Monthly (and on feature drift): full retrain +
   `embedding_evaluation_report` (proxy eval suite per
   `docs/representation/model-selection.md`, ADR-011/015) + a quality gate
   that rolls back if the eval diverges beyond threshold.
4. All runs are recorded to a run-history artifact (W&B or MLflow per
   `docs/representation/training-pipeline.md`) keyed by (run_date, cadence,
   model_id, feature_version).

This matches the user's stated intent ("training was weekly or monthly; data
passovers nightly"). `docs/representation/training-pipeline.md` should be
updated to read "nightly passover; weekly incremental training; monthly full
retrain" rather than "nightly or weekly" — the cadence split here governs.

### D4 (C7) — Dashboard hosting: same domain as sync, on a separate protected route

The dashboard **and its read-side API** are served from the existing domain
`https://mobile-sync.jjrdev.com/` on a **dedicated route prefix**, with auth
+ TLS applied at the domain edge. The sync endpoint
(`POST /api/v1/artifacts/sync`) remains the **write path**. The new route is
the **read+view path**.

| Route | Purpose | Method | Authn |
|-------|---------|--------|-------|
| `/api/v1/artifacts/sync` (existing) | Android app batch upload (write) | POST | device auth token (to be formalized) |
| `/api/v1/dashboard/*` (new) | Read-only queries for the dashboard | GET/POST (query) | user session (authN), read-only role (authZ) |
| `/dashboard/*` (new) | HTML/JS/CSS + streaming UI (WebSocket for live updates) | GET + WS | user session |

Auth model:

- **AuthN** — a user session (password or token) is required to load the
  dashboard. Anonymous is not allowed.
- **AuthZ** — the dashboard account is **read-only** against the artifact
  store. The only path to write to the store is the existing ingest endpoint
  (Android app → `POST /api/v1/artifacts/sync` → `pmbrs_host_sync_ingest.py`),
  and it is device-scoped. The dashboard role must not be granted any write
  scope. This preserves §7 (raw data is authoritative and immutable to
  downstream consumers) and the read-only policy in
  `config/external_data_policy.json`.
- **TLS** — enforced by the domain edge (existing mobile-sync TLS). No
  plaintext HTTP.
- **Local-first escape hatch** — `§16` is preserved: the *same* codebase can
  also be started as a local process reading `~/.pmbrs-private/` directly
  (no domain required). The domain-served instance is an *option*, not a
  mandate. This means the dashboard substrate must not be hard-bound to a
  remote DB or a domain-only API.

This is a **separate route** on the existing domain because reusing the
domain avoids new infrastructure, and the sync endpoint + dashboard share a
host. A new subdomain (e.g. `dashboard.jjrdev.com`) would be equally valid
and can be done later without re-architecting — the domain-level separation
is the durable part.

### Substrate (option 5, chosen)

Per user preference ("whichever is most supported for you to develop"), the
dashboard substrate is **Streamlit + DuckDB** (option B from the
recommendation table) for the first working artifact. Rationale:

- Streamlit is the fastest local-first, read-only, single-user dash tool that
  can be driven from a Python script and hosted either locally or on the
  domain (via a Streamlit server behind the domain's reverse proxy).
- DuckDB reads the raw JSON files directly (via the `StorageAdapter` once
  implemented, or via native JSON reads in the prototype phase) without a
  migration step, and produces the charts that the behavioral-metrics views
  need (timeline, modality coverage, embedding projections).
- It remains **reversible** per §15 (visualization is replaceable): the
  Electron/React vision in `docs/visualization/architecture.md` is the
  forward target once experiments + embedding panels are live; Streamlit is
  the bridge that gets a working artifact in hand first.

Marimo (option A) is a close second and can be swapped in by replacing the
Streamlit entry point — the `StorageAdapter` + views logic is tool-agnostic.

## Consequences

### Positive

- Docs now match the running system. No "where is the data" ambiguity.
- One authoritative raw format (JSON) matches the running pipeline;
  no rewrite of the ingest required.
- JSONL + SQLite layer is preserved as the target for derived/aligned
  artifact types; `StorageAdapter` becomes the single implementation
  decision that unlocks both the dashboard and the ML stubs.
- Cadence semantics are now unambiguous: nightly passover, weekly training,
  monthly full retrain with a quality gate. Downstream tooling (W&B/MLflow
  run grouping, the `pmbrs_hermes_readonly_setup.sh` +
  `pmbrs_publish_summary_to_hermes.sh` chain, the Android WorkManager sync
  worker) can each be wired to its correct cadence without a single "batch
  cycle" term doing double duty.
- Domain reuse for the dashboard avoids new infra; the same codebase runs
  locally or on the domain, preserving §16.
- ADR-017 is the single record; the four decisions (D1–D4) + the substrate
  choice are captured together and are easy to cite when making the
  downstream `StorageAdapter` implementation decision.

### Negative

- Two storage formats coexist (JSON raw, JSONL+SQLite derived). Consumers of
  the store must go through the `StorageAdapter` (or an explicit format gate
  in the dashboard). This is mitigated by the fact that `StorageAdapter` is
  already the prescribed interface in `docs/module-contracts.md`.
- The domain now serves both write (sync) and read (dashboard) on the same
  host. Route separation + authZ must be airtight; a misconfiguration could
  grant the dashboard role write scope. Mitigation: authZ is declared at the
  route level in the dashboard service, not delegated to the ingest service;
  a misconfig on one route cannot affect the other.
- Streamlit + DuckDB is a bridge substrate, not the final form. ADR-018 will
  revisit the visualization stack (Electron/Tauri) once the embedding +
  experiment views are concrete, at which point the Streamlit entry point is
  replaced with the chosen framework without touching the
  `StorageAdapter` or the views logic.

### Neutral / Trade-offs

- The two "declared-but-not-yet-created" subroots (`store/pending`,
  `checkpoints/`) are part of the authoritative tree per
  `config/external_data_policy.json` and will come into existence as the
  ingest queue and the module checkpoints become exercised; this ADR does
  not require them to exist before the dashboard ships.
- ADR-018 (Visualization Layer tech stack) is **not** affected by D4 — D4
  only pins the *hosting* and *auth* of the dashboard, not the *framework*.
  The Electron/React forward target in
  `docs/visualization/architecture.md` remains the eventual target; the
  Streamlit bridge is a provisional implementation of the same conceptual
  views (Timeline, Experiments, Modality Explorer, System Health).
- The `mobile-event-dashboard/` workspace (FastAPI + SQLAlchemy RSVP-event
  service) is a **prior artifact** — it shares the name but is a different
  system. Its `hermes_services/` (tracing, metrics, health) pattern is the
  template for the dashboard's FastAPI surface, but its `Event` model is the
  wrong domain and its relative imports (`from .database import ...`) mean
  it does not run as a standard `uvicorn main:app` target. It should be
  retired as a PMBRS substrate and folded back into the pattern-library
  for `main.py` + `routers/` layout.
